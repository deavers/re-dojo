# RE:DOJO — учебный план лаб и крякми

Утверждённый план (ветка `dojo-labs`). Машиночитаемая версия: [`data/labs_index.json`](../data/labs_index.json),
шаблон лабы: [`Tools_and_Scripts/lab_template/`](../Tools_and_Scripts/lab_template/README.md).

**Правила.** Только собственные бинарники. Никакого обхода защит коммерческого ПО. Малварь — только в изолированной
VM и без сэмплов в репо (в этом плане её нет). Новый C/C++ — в стиле Allman (скобки на отдельных строках),
старые файлы не переформатируются. Тиры и XP существующих 18 позиций не меняются; новые позиции получают тир
по порогам сложности из `rpg_manager.TIERS`.

Структура папки, договорённость по кодам выхода и три обязательных теста (`labNN_build`, `labNN_solve_ok`,

[`Tools_and_Scripts/lab_runner.py`](../Tools_and_Scripts/lab_runner.py).

Сборка (основной компилятор автора — MSVC из Visual Studio 2022; в CI — GCC на Ubuntu и MSVC на windows-latest):

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
```

CI (`.github/workflows/opsec_and_integrity_ci.yml`): push в `main`, `master`, `dojo-*` и PR — Linux-задача
(GCC) запускает `ctest -LE "windows|unity"`; задача `windows-labs` (MSVC, все тесты кроме `unity`) — только на PR
и на `main`.

## 4. Лабы на карте

* Источник правды — `data/labs_index.json`: `status` (built / planned), `prereqs`, `trains`, `check`, `platform`.
  Строка в таблице Dojo в README нужна только собранным лабам; сборщик сверяет её с индексом (тир, сложность).
* Рёбра лаба → лаба берутся из `prereqs` (неявной цепочки LabN → LabN−1 больше нет).
* Рекомендации игре: для каждой её техники — **две самые лёгкие собранные лабы**, у которых техника есть в `trains`.
* Запланированные лабы в `redirect_labs` ограниченных узлов показываются текстом
  (`safety.redirect_labs_planned`): без ребра и без ссылки из подсказки, пока лаба не собрана.
* На плитке лабы — подписи «только Windows» и «нужен Unity».

## Шаблоны категорий

Базовый шаблон — [`Tools_and_Scripts/lab_template/`](../Tools_and_Scripts/lab_template/README.md). Ниже — только

### Категория «VMT / виртуальные методы» (образец: Lab 32)

* **Файлы:** как у лабы на память (`labNN_core.hpp`, `check/labNN_selftest.cpp`, `solve/solve.py`, README).
* **Ядро:** иерархия с одиночным наследованием и **без виртуального деструктора** — тогда раскладка таблицы
  одинакова в MSVC и GCC (vptr на +0x00, слоты по порядку объявления, 8 байт). Вызовы — через
  `IPerson* volatile` (массив-«ростер»), иначе компилятор девиртуализирует вызов и правка vptr ни на что не
  влияет. Донор — объект другого класса, у которого нужный слот уже делает «правильное» и не трогает поля.
* **Selftest:** корневой объект — массив целевых объектов; `h.donor` — донор; исходные таблицы регистрируются
  `readOnly = true`. Команды харнесса: `vcopy <off> <nslots>` (теневая копия) и
  `vset <off> <slot> donor <dslot>`.
* **Обязательные неверные ответы:** правка общей таблицы (отклоняется как запись в read-only), не тот объект,
  не тот слот, «все объекты сразу», `vcopy` за конец таблицы, «vptr» не по тому смещению.
* **Отличие от базового шаблона:** проверяется не значение поля, а поведение виртуального вызова; условие
  победы обязательно проверяет и «только этот объект».

### Категория «Крякми с виртуальной машиной» (образец: CM 17)

* **Файлы:** только `crackmeNN_<name>.cpp`, `solve/solve.py`, `check/expected.json`, README (selftest не нужен:
  крякми читает stdin, тесты гоняют сам бинарь).
* **Байткод** генерируется ассемблером вне репо (ключ в репо не попадает) и вставляется в `kProgram[]`.

* **`solve.py`** не хранит ключ: извлекает `kProgram` из исходника регуляркой, дизассемблирует и решает

### Категория «Эмуляторы» (образец: Lab 54)

* **Файлы:** как у лабы на память (`core.hpp` с машиной, `check/selftest`, `solve.py`, README).
* **Ядро:** статический объект машины (`g_Machine`) с указателем на гостевую RAM в куче; при старте — мусорное

### Категория «Чекер артефакта / мини-UE» (образец: Lab 45)

* **Файлы:** `core.hpp` (структуры движка + построение), `labNN_<name>.cpp` (игровая цель с флагом), `check/labNN_selftest.cpp` —
  **чекер**: строит те же структуры в своей памяти и сравнивает с артефактом ученика со stdin; `solve/solve.py` —

  запись, испорченная строка. `"runs": 3` — раскладка в куче случайна.
* **Отличие от базового шаблона:** selftest — не применение правок, а сравнение артефакта; настоящий exe
  проверяется вручную на игровом пути (у Lab 45: три имени → флаг, код 0, неверные → 1). Lab 46 / 47 / 59 / 66

### Категория «Встроенная Lua» (образец: Lab 52)

* **Файлы:** как у лабы на память + `LIBS lua54` в `dojo_add_lab` (Lua 5.4.9 из `third_party/lua`, без изменений, MIT,
  собирается как `lua54.dll` / `liblua54.so`). Метка `windows` (практика — внедрённая DLL), но сборка и тесты
  переносимы и идут и на GCC.
* **Ядро:** статический объект движка с `lua_State*` по известному смещению; скрипт игры — строка в `core.hpp`;
  песочница: только base / table / string / math, `dofile` / `loadfile` = nil. Победа читается из Lua с проверкой
  **типов** (`lua_getfield(...) == LUA_TNUMBER`), а не только значений.
* **Selftest моделирует внедрённую DLL:** `luado <смещение> <код>` читает указатель из движка, **сверяет с настоящим
  `lua_State`** (иначе код 2, ничего не разыменовывается) и выполняет код через `luaL_dostring`; ошибка Lua = код 1.
* **Обязательные неверные ответы:** не то смещение, не то значение, глобальные вместо полей таблицы, неверный тип,
  `os.exit` (песочница), синтаксическая ошибка.
* **Подводные камни:** `LUA_BUILD_AS_DLL` только для `WIN32` (иначе `__declspec` ломает GCC); предупреждения Lua
  глушатся только для цели `lua54`; проверить экспорт `lua54.dll` (`luaL_loadstring`, `lua_pcallk`).
* **Отличие от базового шаблона:** правка идёт кодом в чужой VM, а не байтами; Lab 53 / 57 / 61 / 67 добавляют вызов
  из DLL, метатаблицы, байткод `luac` тем же `luado`.

### Категория «Z3 / символьное исполнение» (образец: CM 16 — **черновик, крякми ещё не собрана: нет z3-solver**)

* **Файлы:** как у крякми (`crackmeNN.cpp`, `solve/solve.py`, `check/expected.json`, README); `solve.py` импортирует
  `z3` (пакет `z3-solver`).
* **Задача:** ключ — несколько 32-битных чисел, проверка — система связанных ограничений (сложение, XOR, сдвиги,
  умножение по модулю 2^32), которую вручную решать долго. Решение **единственное**: при разработке z3 проверяет,
  что `key != найденный` даёт `unsat`.
* **CTest:** тесты получают метку `z3`; если `import z3` недоступен, runner завершает тест с понятным сообщением.
  CI: в Linux-задачу добавляется `pip install z3-solver` (вместе с первой Z3-лабой), в `windows-labs` — тоже.
* **Обязательные неверные ответы:** одна компонента ±1, компоненты переставлены, решение ослабленной системы
  (без одного ограничения), неверный формат (код 2).
* **Отличие от базового шаблона:** эталон — решатель, а не готовый ответ; `expected.json` строится из ключа,
  заданного генератором, и сверяется с моделью z3.
